# Security and data safety

## Phase 3C push boundary

Push requires an existing upstream and advertised destination branch. A locked prepared object binds registered directory identities, branch, HEAD, supported local config, remote URL, and fully qualified target. Fresh constrained fetch establishes the remote target before confirmation and again afterward. Changed approval inputs, remote advancement/deletion, non-ancestry, hooks, push URLs/refspecs/mirror settings, and unsupported configurations block publication. The isolated source ref contains only the approved commit. One fixed non-force refspec is executed, with tags, recursion, signing, hooks, implicit defaults, redirects, and arbitrary helpers disabled. Saved gh credentials are used only through the fixed official helper. Local bare fixture remotes are also checked for unsafe configuration/hooks.

The 120-second bounded process-group runner distinguishes redacted authentication/network/rejection errors. After the durable dispatch boundary, cancellation or failure can be uncertain. A separate exact-ref query reconciles publication when possible; exit zero alone never establishes success. Sync refresh and durable success must also finish. Unfinished journals become uncertain on startup without any remote request. No retry, rollback, force, tag update, ref deletion, or first-time publication is exposed. Ordinary server-side races can reject the push; remote deletion/recreation between observations cannot be eliminated without a remote compare-and-swap protocol. Remote state can change immediately after verification. This is a point-in-time result, not a backup guarantee. Working files and the original index are never written by pushing.

## Phase 3D index and commit boundary

Review binds one opaque token to a registered repository and bounded in-memory index/working-file snapshot. Status and numstat use NUL records; paths are validated as exact relative files and passed with literal pathspecs and NUL input. Traversal, metadata/attribute/submodule paths, symlinks, hardlinks, special/shared-write files, sparse/hidden/unmerged index entries, and unknown config are rejected. No caller supplies Git arguments or shell fragments. Diff text is transient, capped at 512 KiB, rendered as text, and excluded from journals/logs; binary files get indicators instead. Native errors withhold raw Git stderr.

Stage and unstage are separate fixed commands against an exclusively created private index. Git's native `index.lock` reserves the original index. Original index bytes/identity, branch/HEAD/config and reviewed working-file snapshots must still match before the private result is installed with a synced write and atomic rename. Only selected file paths (plus a displayed rename's old path) enter Git. Unstage uses index-only `restore --staged --source=<reviewed HEAD>`; it cannot update working files. The backend removes only its own descriptor-verified live lock, never a preexisting or replacement lock. Crashes can retain locks and stages.

Commit approval binds the staged tree, parent HEAD, local branch, message, and resolved author. Direct global author files are parsed with `--no-includes` outside the repository; only name/email enter execution. Local identity overrides global identity. Includes, global hook overrides/signing requirements, invalid identity, and non-sample repository hooks block committing. No settings are modified. Hooks, signing, tests, message generation, amendments, empty commits, branch creation, and automatic pushes are absent.

Unsigned `commit-tree` creates the approved staged tree with one existing parent. Native index and HEAD reservations protect publication; a private detached metadata view with an explicit common directory lets `update-ref --no-deref` compare-and-swap the named branch without Git's implicit HEAD transaction conflict. Symbolic local branch aliases are rejected. Branch reflog records publication; the main HEAD reflog is preserved. Post-publication verification checks HEAD, tree, parent, and unchanged original index before sync refresh and durable completion. Abandoned prepublication objects do not change branch history. Database or verification failure after publication remains uncertain.

Local mutation subprocesses are not killed on timeout/cancellation once started; output is drained with bounded memory. Cancellation is honored before index installation or branch publication, then deferred through verification. Stalled Git/storage can hold the queue indefinitely. Startup marks unfinished change journals as requiring inspection. Every consumed token requires a fresh HEAD/index review for another mutation. Journals store paths and object IDs, not contents/messages. Retained stages contain index metadata, and staged/committed content necessarily exists in Git objects.

These checks assume trusted current-user software and a local filesystem. They are not an OS sandbox against malicious same-user writers, directory replacement, direct ref writes bypassing locks, or power loss. Index/refs, working-file observations, and SQLite are not one transaction. Clean status never permits removal. Limits: 10,000 changed entries, 1,000 selected entries, 8 MiB/changed file, 32 MiB combined changed-file snapshots/index, and 64 KiB messages; intermediate inspection output retains its existing limits. Large/special repositories require terminal handling.

## Trust boundaries

The renderer is local bundled application code. It selects roots and requests narrowly scoped commands; Rust owns filesystem/Git/database operations. IPC accepts scan paths from the renderer, not a backend-maintained directory grant list, so renderer compromise could request scans elsewhere readable by the user. The CSP and absence of remote content reduce exposure; they do not constitute an OS sandbox.

Repositories and their configuration are treated as untrusted inputs. The system Git binary, Rust runtime, SQLite, Tauri, OS, and application build are trusted. Users should keep system Git patched. The initial implementation is intended for development repositories controlled by the current user, not adversarial multi-user directories.

## Implemented read-only execution policy

- Fixed Git binary candidates and argument arrays; no shell interpolation, user-provided executables, or arbitrary command IPC.
- Clear inherited environment; fixed system PATH and C locale. Inherited `GIT_DIR`, `GIT_WORK_TREE`, `GIT_CONFIG_COUNT`, tracing, executable helpers, and alternate-object environment variables do not propagate.
- Disable system/global Git config. Repository config remains subject to normal Git ownership checks; no `safe.directory` override is used.
- Resolve standard `.git`/`commondir` pointers and parse the explicit config file from outside the repository with `--file` and `--no-includes`. Check pointer/config types and size bounds before parsing. Reject config includes, all configured filters, `core.worktree`, bare storage, promisor/partial-clone settings, and unsupported extensions before working-tree status.
- Command-line settings override repository hooks, filesystem monitors, external diff, pager, global attributes/excludes, untracked-cache updates, preload index, submodule recursion, protocol access, and credential helpers.
- Disable optional locks and lazy fetching; null stdin and terminal prompting disabled. No network Git commands exist in the inspection adapter.
- Status uses NUL-delimited porcelain, no rename detection, and ignores submodule working trees. Filenames are counted without decoding them as instructions or HTML.
- Limit each subprocess to 15 seconds and 4 MiB output per stream; drain both pipes, cancel/kill/reap on timeout, cancellation, or overflow.
- Raw Git stderr and raw config are never sent to the renderer or stored in SQLite. Errors have safe messages and structured codes. URL userinfo, query strings, and fragments are removed before remote metadata leaves the adapter; unusual URL syntax is withheld.
- Application-data directory permissions are `0700` on Unix. SQLite access is private to Rust and parameterized.

Tests exercise malicious fsmonitor, external diff, hooks, credential helpers, and filters; include rejection; URL redaction; path metacharacters; symlinks; and cancellation. These are supporting evidence for these specific controls, not a claim of complete hardening.

## Unsupported configurations and limits

Bare repositories, independent submodule registration, Git LFS/other configured filters, includes/conditional includes, redirected worktrees, worktree-specific configuration extensions, partial clones, unsupported object formats, symlinked `.git` markers, and non-UTF-8 metadata/paths fail closed. Standard linked worktrees are supported, including their external Git metadata. Broken Git/config files surface a generic Git error without exposing their raw contents.

Directory traversal skips symlinks and known dependency/build folders. Selected roots are canonicalized, but only the final selected component is checked for a symlink. Intermediate aliases can resolve during canonicalization. Git internals may refer to metadata outside the selected root, including linked-worktree common directories and object alternates. This implementation does not sandbox Git's filesystem reads or fully validate every internal metadata reference.

There is a check/use race if another process replaces a directory, `.git` file, or repository config during inspection. Git itself can inspect content beyond initial filesystem checks. The policy does not defend against malicious concurrent mutation; a future stronger threat model requires descriptor-based traversal and OS process isolation. Subprocess supervision is for Git itself, not arbitrary process trees; the policy prevents tested helper launches, but process-group isolation is not implemented.

Per-command bounds do not provide a hard wall-clock deadline for an entire scan. Standard filesystem calls may block on network/removable filesystems. Use local directories. Scan traversal and output memory are bounded, but Git's internal CPU/memory use is not OS-limited. Progress counts are traversal work units (entries and directory visits), not a unique file census.

Sanitization recognizes conventional credential locations. Secrets deliberately placed in URL path segments, repository names, or branches cannot reliably be distinguished from legitimate metadata. Those values are displayed as text, never markup or executable URLs. No tokens/account credentials should be entered into Stow; authenticate only through official gh/Terminal/browser prompts.

## Future destructive workflows

Creation-only cloning and separately constrained fetch, fast-forward pull, single-branch push, index editing, and commit policies are described below. Reset, destructive checkout, clean, archive, and delete commands are not exposed. Unregistering deletes only one registry record. A clean working-tree count is not evidence that data is recoverable: ignored files, local branches, reflogs, unpublished objects, submodules, and external assets are outside this inspection slice.

Before adding Stow Project or removal: build a separate mutation policy, verify remote and backup recovery, review exact deletion boundaries, protect linked worktrees and symlinks, capture a recoverable plan, require explicit destructive intent, and test interruption and restoration. Never infer permission to delete from a scan or clean status.

## Phase 2A GitHub boundary

The Git command policy is unchanged. A distinct private gh runner allows only version, authentication status without `--show-token`, GET `/user`, and paginated GET `/user/repos` with fixed host/parameters. No renderer command accepts shell text, executable paths, provider endpoints, API methods, or environment variables. Stow never invokes `gh auth token`, reads credential files, intercepts login output, or persists raw API/authentication responses. Only gh accesses its credential store/keychain. gh may itself store credentials according to its official platform behavior; Stow does not replace that credential manager.

Fixed gh paths include Homebrew, conventional manual install, MacPorts, and system locations. Repository PATH and working directory are not used. Symlinked package-manager installations are allowed as trusted user/system software. The runner starts at `/`, clears inherited environment, and sets a fixed system PATH, locale, GitHub.com host, disabled prompts/update notices, and noninteractive pager. Only absolute HOME/gh configuration directories are retained. Token overrides, proxy variables, TLS overrides, debug logging, custom browsers/pagers, and repository variables are excluded. Custom corporate proxy/certificate setups are therefore not currently supported. Config directory locations are trusted launch configuration; built-in gh commands are used, never aliases/extensions.

CLI stdout is bounded at 32 MiB, stderr at 1 MiB; both are concurrently drained. Timeout, cancellation, overflow, and wait errors kill/reap the child; raw stderr is used only for constant error classification and then discarded. Version checks have a 5-second limit, auth and identity calls 30 seconds each, and the paginated call 120 seconds. The whole operation can include several such calls. Supervision bounds the direct child, not arbitrary descendant processes; trusted gh/OS helpers are outside a full process-tree sandbox. Auth checks may query configured Enterprise hosts to detect their status, but repository API calls only target GitHub.com. Unsupported/ambiguous diagnostics become uncertain, not a guessed usable login.

API inputs are untrusted. Stable positive IDs, bounded safe owner/repository names, canonical URLs, visibility consistency, bounded description/branch text, timestamps, array shapes, page/repository counts, and duplicate identities are validated before the cache transaction. Unknown fields are ignored rather than persisted. JSON parse errors never include raw response text. Arbitrary secrets disguised as valid repository metadata cannot be detected reliably. The UI renders metadata as text. External URL opening revalidates the cached owner/name and canonical URL, accepts no arbitrary frontend URL, and passes one fixed-host HTTPS URL to `/usr/bin/open` without a shell.

User-initiated login is the only interactive command. `/usr/bin/osascript` sends a controlled command to Terminal for official browser login. The executable is allowlisted, the arguments are fixed, and OS home/config paths use AppleScript's `quoted form` before entering Terminal's shell. Login uses a cleared environment and does not pass credentials through Stow. The OS may require Terminal Automation authorization; denial returns a safe error plus manual-login instructions. Stow never grants that permission itself. Login is not proof of success: the user must recheck.

Per-account memberships prevent one account refresh from marking another account's repositories inaccessible. All cached accounts belong to the same local application/OS user; switching gh accounts does not hide or wipe previously cached private metadata. Cache records and local/remote links are metadata history, not verified backup/recovery claims. Repository renames and URL reuse cause historical-link uncertainty. A successful accessible-list response can still be incomplete because of permissions or concurrent server changes. No mutation, archive, cleanup, or deletion eligibility is inferred.


## Phase 2B clone and editor boundary

Cloning is a separate private command policy in `clone.rs`; the read-only Git policy is preserved. IPC accepts a cached GitHub repository ID/account and a root/name, never a URL, executable, shell fragment, refspec, or environment. GitHub GET `/repos/{owner}/{name}` validates stable identity and canonical HTTPS URL before and after population; rename/reassignment or a changed default branch fails safely. Redirects and all protocols other than HTTPS are disabled. The CLI credential helper is a fixed allowlisted `gh auth git-credential` invocation. Credentials flow directly between Git and gh; Stow never receives or persists them. Saved gh authentication is used; global Git credential helpers, URL rewriting, and token environment overrides are excluded.

The population sequence uses fixed `init --template=`, origin configuration, creation-only fetch, ref setup, and checkout into a newly created repository. Using this sequence instead of `git clone` prevents Git's failed-clone cleanup from removing the staging repository. It does not permit fetching into an existing workspace. Environment is cleared; global/system config, hooks, filesystem monitors, configured filters, templates, global attributes, submodule recursion, automatic maintenance, and terminal prompts are excluded/disabled. HTTPS verifies TLS; fetched objects undergo fsck. Git's HFS/NTFS checkout protections are enabled. LFS pointers remain pointers, and submodule contents are not populated. Stow runs no repository build/setup scripts.

Every root component is opened with `openat(O_NOFOLLOW|O_DIRECTORY)`. Roots must belong to the effective user and lack group/world write bits. macOS extended ACL entries are rejected conservatively, including inherited entries; Stow does not rewrite permissions. Staging is exclusive `mkdirat(0700)` under that pinned root, with a random 128-bit identifier. Device/inode identities and path bindings are revalidated at creation, execution, verification, promotion, and recovery. A root advisory lock serializes cooperating Stow processes. Promotion uses macOS `renameatx_np(RENAME_EXCL)` with source/destination directory descriptors, never an overwrite-capable fallback. Existing files, directories, and dangling symlinks all collide. A preview confers no authorization over later filesystem state. Scanning excludes `.stow-clone-*` components, including explicitly selected staging roots.

The only new dependency is a direct declaration of already-transitive `libc`, needed for directory descriptors, no-follow traversal, exclusive rename, flock, and process groups. Git children run in a dedicated group; cancellation, timeout, output overflow, or process completion kills remaining transport/helper descendants and reaps the direct child. Clone Git work has a shared 15-minute deadline and 8 MiB per-stream bounds. Only recognized numeric receiving-object percentages reach the UI; raw diagnostics are discarded. GitHub identity calls and read-only verification retain their separate existing limits. Filesystem calls and Git's internal memory/disk consumption are not OS quota-limited.

Schema 3 records intent before filesystem creation, then staging identities, verification snapshot, promotion intent, promotion result, and registration. Filesystem and SQLite are **not one atomic transaction**. Project insertion and journal completion share one SQLite transaction. A failure after promotion leaves the destination intact; recovery recognizes the recorded inode, rechecks remote/branch/commit/cleanliness, then attempts registration. Recovery never resets changed files, adopts an unrelated destination, or promotes an unverified partial clone. Journals and staging are never automatically deleted. A crash before a directory identity reaches SQLite may require manual review of the recorded path. Recovery of verified data uses the recorded identity and local inspection, without requiring another network fetch.

This is not a sandbox against malicious processes running as the same user, compromised trusted Git/gh binaries, or privileged attackers. Same-user mutation of repository internals between checks cannot be completely excluded. Network/removable filesystems and power-loss durability have not been verified; use private local workspace directories. Directory synchronization and SQLite transactions support ordinary process-interruption recovery, not a claim of full storage-device crash consistency. If Stow is forcibly terminated during fetch, an orphan Git/helper may finish writing its private unverified stage; that stage is never eligible for automatic promotion or cleanup.

Editor IPC resolves a registered project ID to its stored path, rejects symlink components, and selects a fixed VS Code/Cursor bundle CLI or `/usr/bin/open -R`. No frontend executable or extra arguments are accepted. The environment is cleared and the handoff has a 15-second bound. Code/Cursor receive `--new-window --disable-extensions`; Stow does not accept workspace-trust dialogs. Editor global settings, trust decisions, automatic tasks, and actions after handoff are outside Stow's execution policy. Finder remains an explicit fallback. Editor failure is recorded separately and never changes a successful clone's state. A successful process exit proves handoff only, not a rendered editor window.

## Phase 3A synchronization and fetch boundary

Fetch is an explicitly authorized metadata mutation, separate from inspection and creation-only clone policies. IPC accepts a registered project ID, current assessment token, and a validated configured remote name; there are no URL, flag, refspec, executable, environment, or shell parameters. Execution revalidates the pinned root/.git identity, HEAD/branch, upstream, remote configuration, paths, and operation markers. A first explicit sync inspection binds existing registrations; a later identity mismatch requires deliberate unregister/rescan rather than silently adopting replacement data.

Supported targets are canonical GitHub.com HTTPS URLs without credentials/query/fragment or absolute private local bare-repository paths. Other transports, SSH commands, custom upload packs, helpers, HTTP overrides, configuration includes, URL rewriting, and extra configuration fail closed. The fetch config vocabulary permits ordinary core metadata, user name/email, remote URL/fetch/pushurl declarations, and branch remote/merge declarations. The selected remote must have exactly one URL and standard heads-to-remote mapping. A conventional leading `+` in that declaration is recognized but **never executed**. Source local bare repositories have an even smaller core-only config vocabulary. Global/system Git configuration and inherited Git/token/proxy/TLS/executable overrides are excluded. HTTPS uses TLS verification and no redirects; only the fixed saved-login gh credential helper is allowed. Raw stderr/config/credential responses are never persisted or displayed. Validated credential-free transport identifiers are persisted to distinguish freshness after URL changes.

Private local ordinary `.git` directories are required for fetch. Every directory path component is opened without following symlinks. Root and metadata directories must be owned by the effective user without shared write permissions or extended directory ACL entries. Metadata traversal is bounded at 100,000 entries and rejects symlinks, hardlinked files, special files, foreign ownership, shared write bits, and lock files. Linked/shared worktrees, alternates, grafts, shallow/partial/replace-ref history, unsupported object formats, and custom mappings are rejected. Existing linked-worktree inspection remains available. Advisory root/.git locks serialize cooperating Stow instances; the app queue prevents overlap with its clone/inspection/registration operations. External tools do not honor Stow's advisory lock, so Git's expected-old ref assertions and post-inspection detect relevant concurrent changes.

Each fetch gets an exclusive private `.git/.stow-fetch-<random-id>` bare repository. The network command operates there with hooks, monitors, submodules, tags, templates, lazy fetch, and maintenance disabled. Its `GIT_OBJECT_DIRECTORY` points to the validated original object store, avoiding duplicate objects. The selected cached tracking refs seed staged **heads**, whose Git fast-forward rules reject rewinds without `--force`; direct fetch into `refs/remotes` would not provide that guarantee. Fixed atomic fetch uses no force/prune/tags/FETCH_HEAD write. Successful staged refs are applied through expected-old `update-ref` assertions, with no dereferencing and a HEAD guard, only to `refs/remotes/<selected>/...`. No branch, index, checkout, worktree, or repository script command is run. Git 2.46+ is required for symbolic HEAD verification. See [Git fetch namespace semantics](https://git-scm.com/docs/git-fetch) and [ref transactions](https://git-scm.com/docs/git-update-ref).

Revalidation occurs before applying refs. A symbolic HEAD assertion prevents the transaction from following a switched HEAD; detached HEAD has an expected-object assertion. An attached branch's concurrent commit is detected by post-inspection rather than combining incompatible HEAD/branch assertions in Git. Stow never writes that branch. Git ref transactions are not advertised as filesystem-wide atomic snapshots or power-loss-proof commits. Cancellation, abrupt termination, or database failure can leave objects, lock files, staging refs, or applied tracking updates. Reinspection after ordinary failure uses a fresh cancellation token; no failure becomes success, no rollback is claimed, and no stage/lock is deleted. A forced app exit may leave a Git child finishing metadata writes, so unfinished journals require review. No success time is recorded until ref application and reinspection finish and SQLite accepts completion.

Fetch reuses clone's bounded process-group supervisor: 15-minute transfer/application deadline, 8 MiB output per stream, fixed numeric transfer progress, and group kill/reap on cancellation, timeout, overflow, or completion. Read-only validation has its existing per-command limits and is outside that transfer deadline. Git objects, retained staging refs, and durable history have no disk quota or automatic retention cleanup. Metadata checks add filesystem work; large repositories may hit conservative limits.

The existing private-local-filesystem threat model remains: this is not an OS sandbox against malicious same-user/privileged processes replacing internals between checks. Identity pinning and descriptor execution reject tested workspace substitution; Git still performs path-based internal I/O. Avoid network/removable/shared filesystems. Trusted Git/gh must be kept patched. Live private/SSO authentication, power loss, and platform variants need separate verification. Successful fetch proves only a completed contact at that time, not current reachability, all-branch publication, push completion, or remote recoverability.


## Phase 3B: fast-forward integration boundary

`pull.rs` is a separate integration policy. The frontend supplies only a registration ID and sync token, then a backend-generated journal ID and confirmation boolean. The existing single-operation queue reserves admission before preflight; root/.git descriptor locks remain held across confirmation (maximum five minutes), fetch, validation, integration, and verification. Invalid/stale source state requires fresh review. Failed preflight attempts are journaled for registered IDs. Legacy registrations first acquire their workspace identity through the existing explicit sync inspection; later substitutions are rejected.

Only a clean ordinary checked-out SHA-1 branch with exactly one configured remote/upstream and a standard fetch mapping can proceed. Git 2.46+ and Phase 3A's transport/config/history restrictions apply. The fetch policy now records verbose porcelain results so pull can distinguish actually advertised refs from retained deleted branches. The selected upstream must be advertised in that successful fetch and match its tracking object. All other ref changes must exactly match the fetch report. The local branch must be an ancestor of the target; ahead-only/diverged histories are refused. No implicit upstream selection is used for integration.

The mutation policy rejects ignored files as well as untracked files (Git can otherwise overwrite ignored obstructions), assume-unchanged/skip-worktree/unmerged index entries, non-sample hooks, hook configuration, filters/includes/helpers and all other settings outside the closed fetch vocabulary, local attributes, sparse metadata, submodule storage, and attributes/submodules/symlinks in either revision. Private ordinary metadata and working files are checked for ownership, shared write access, redirection, hardlinks and special files. Traversal is bounded at 100,000 entries, index snapshot at 32 MiB, and tree/ref command output by the existing inspection limits. Unsupported layouts are blocked rather than rewritten. Global attributes/configuration and inherited environment are disabled.

The runner accepts only one validated hexadecimal commit ID. It invokes fixed Git with `merge --ff-only --no-edit --no-stat --no-progress --no-overwrite-ignore --no-autostash --no-verify --no-gpg-sign <OID>`, a cleared environment, disabled hooks/fsmonitor/credentials/protocols/submodule recursion/signing/maintenance, and descriptor-pinned working directory. There are no shell strings, arbitrary renderer flags, merge commits, rebases, force updates, resets, prune operations or automatic conflict resolution. Git may write ORIG_HEAD/reflogs in addition to HEAD, the current branch, index and working files; unrelated local refs are checked before and after. It can leave partial filesystem changes on error. **No multi-file/ref/database atomicity is promised.**

Cancellation is checked before fetch, supervised during fetch, and before integration. After the durable `integrating` boundary, cancellation is deferred: integration runs without kill/timeout, with output discarded to avoid pipe/memory pressure, in a separate process group. Stow waits for exit and verifies clean status, HEAD, branch, config and refs with a fresh non-cancelled inspection. A user cancellation request during this section can therefore end in verified success. A hung storage/Git operation can hold the queue indefinitely; do not terminate it casually. App termination/power loss can interrupt Git or leave it running. Startup marks every unfinished pull `requires_inspection`, preserving phase/target; it does not infer success from HEAD alone. Failed exit, failed verification, and failed durable success recording are also uncertain. Manual inspection is required; no automatic reset, lock removal, cleanup, resume or retry occurs.

As with Phase 3A, advisory locks coordinate Stow instances, not editors or arbitrary Git processes. Repeated identity/config/index/ref/status checks detect observed interference, and Git's native locking/checkout checks add protection, but there is no OS sandbox against malicious same-user concurrent mutation between validation and use. Keep external Git tools and file writers idle; this supported policy assumes a trusted local filesystem/user. File contents and configs can change after any check, and a remote can advance after fetching. Stronger process/filesystem isolation and power-loss validation remain outside this slice. No user/global Git configuration is changed.
